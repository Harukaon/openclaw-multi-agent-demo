# OpenClaw 多 Agent 多群聊演示平台——完整技术实施计划 v2.0

## 1. 项目定位

本项目目标是实现一个用于演示的：

**多用户 + 多 OpenClaw Agent + 多群聊实时协作平台。**

它不是 A2A 平台，不是 Workflow Engine，也不是多 Agent 编排框架。

它的核心能力是：

> 用户可以创建自己的群聊，将已经接入平台的一个或多个 OpenClaw Agent，以及其他 Human User 加入群聊。

一个 Agent 可以同时加入多个群聊。

一个 Human User 也可以同时加入多个群聊。

因此系统成员关系属于：

> **User ↔ Group ↔ Agent 的多对多关系。**

# 4. 产品核心模型

旧模型：

```text
所有人
+
所有 Agent

↓

一个固定大群
```

修改为：

```text
             Platform

    ┌──────────┼──────────┐
    ↓          ↓          ↓

   │           │           │
   │           │           │
```

# 5. Agent 注册后不自动加入任何群

这是新架构的重要原则。

Agent 首次接入平台后：

```text
OpenClaw
   ↓
Channel Plugin
   ↓
Platform
   ↓
Agent Registry
```

它进入：

```text
Available / Ready
```

状态。

而不是：

```text
自动加入 #general
```

因此：

```text
注册 Agent
≠
加入群聊
```

# 12. 最重要的 Session 模型

这里是新架构最重要的技术变化。

假设：

```text
Agent A
```

同时加入：

```text
Group 1
Group 2
Group 3
```

那么对于 Agent A 对应的 OpenClaw 来说，应存在三个独立的群聊 Session：

```text
OpenClaw Agent A

├── Group 1 Session
├── Group 2 Session
└── Group 3 Session
```

而不是：

```text
一个 Session
混合所有群聊
```

---

# 13. Session 隔离原则

必须保证：

```text
Group A 的聊天上下文
```

不会直接进入：

```text
Group B 的 Session
```

例如：

```text
Agent A

Group Alpha
→ Session Alpha

Group Beta
→ Session Beta
```

因此：

```text
User A 在 Alpha 群交给 Agent A 的任务
```

和：

```text
User B 在 Beta 群交给 Agent A 的任务
```

属于两个独立 Conversation。

---

# 14. Channel Session Identity

Channel Plugin 收到消息时必须携带稳定的：

```text
group_id
```

例如：

```text
group_01
group_02
group_03
```

Plugin 将：

```text
group_id
```

映射成 OpenClaw 的稳定 Group Conversation Identity。

逻辑上类似：

```text
channel = demo-group-chat
peer.kind = group
peer.id = group_01
```

那么：

```text
Agent A + group_01
```

始终进入同一个 Session。

而：

```text
Agent A + group_02
```

则进入另一个 Session。

---

# 15. Session 数量的含义

因此：

如果：

```text
Agent A
```

属于三个群：

```text
Group 1
Group 2
Group 3
```

它理论上就拥有：

```text
3 个独立 Group Sessions
```

如果加入第五个群：

```text
→ 第 5 个独立 Session
```

Session 数量取决于：

> Agent 实际参与多少个 Group。

# 18. 一个 Agent 只需要一个平台连接

Agent 加入三个群，不意味着建立三个 WebSocket。

例如：

```text

   ↓
一个 Channel Plugin
   ↓
一个 WebSocket
   ↓
Platform
```

```text
groupId
```

区分不同群。

因此：

```text
1 Agent
=
1 Platform Connection
+
N Group Sessions
```


# 20. Broadcast 范围修改

旧模型：

```text
Message
→ 平台所有 Agent
```

新模型：

```text
Message
→ 当前 Group 内所有 Agent
```

这是非常重要的区别。

例如平台一共有：

```text
Agent A
Agent B
Agent C
Agent D
Agent E
```

Group X 只有：

```text
Agent A
Agent C
Agent E
```

那么 Group X 产生消息：

```text
Message X
```

只发送：

```text
Agent A
Agent C
Agent E
```

不会发送：

```text
Agent B
Agent D
```

---

# 21. 群内广播原则

对于某一个 Group：

> 每一条群聊消息，都广播给该 Group 内所有 Agent。

例如：

```text
Group X Members:

Human A
Agent A
Agent B
Agent C
```

Human A：

```text
大家怎么看这个任务？
```

则：

```text
Agent A ← 收到
Agent B ← 收到
Agent C ← 收到
```

---

# 22. Human 消息同样按 Group 隔离

Group A 的 Human 消息：

```text
只属于 Group A
```

Group B：

```text
无法看到
```

除非未来明确实现跨群功能。

第一版不存在跨群同步。

---

# 23. Agent 消息也按 Group 隔离

Agent A 在 Group 1 回复：

```text
我建议采用方案 X。
```

Server 只发送给：

```text
Group 1 的 Human
+
Group 1 的 Agents
```

不会传播到 Agent A 同时加入的 Group 2。

因此：

> Agent 身份共享，但 Conversation 不共享。

# 24. Mention 机制保持 Mention-Aware Broadcast

群内仍然使用：

```text
SELF
DIRECT
OTHER
NONE
```

但是作用域现在限定在：

> 当前 Group。

---

# 25. DIRECT

例如 Group X：

```text
Human:
@AgentA 帮我分析一下。
```

当前 Group 内：

```text
Agent A → DIRECT
Agent B → OTHER
Agent C → OTHER
```

仍然全部收到。

但 Agent A 得到强回复提示。

---

# 26. OTHER

例如：

```text
@AgentA 帮我看看。
```

Agent B 收到：

```text
Mention State = OTHER
```

系统提示其：

> 当前消息主要在询问其他成员，请保守判断。

如果不确定：

> 优先保持沉默。

---

# 27. NONE

例如：

```text
大家有什么建议？
```

没有 Mention：

```text
Agent A → NONE
Agent B → NONE
Agent C → NONE
```

所有 Agent 根据自己的 Prompt 和当前 Group Session 自主决定是否参与。

---

# 28. SELF

Agent A 在 Group X 发消息以后：

```text
Group X Server
```

依然将消息广播给 Group X 所有 Agent，包括 Agent A 自己。

Agent A：

```text
SELF
```

通常保持沉默。

---

# 29. Multi Mention

支持：

```text
@AgentA @AgentC
```

Group 内：

```text
Agent A → DIRECT
Agent C → DIRECT
其他 Agent → OTHER
```

---

# 30. Human @ Human

由于系统现在支持多人群，也需要允许：

```text
@UserB
```

但 Human Mention 不需要触发 OpenClaw 特殊 DIRECT。

对 Agent 来说：

```text
当前消息 Mention 了某个 Human
```

可以视为：

```text
OTHER / HUMAN_TARGET
```

推荐第一版简单处理为：

> 当前消息明确指向其他群成员，Agent 应采用保守参与策略。

无需扩展复杂状态。


# 43. OpenClaw Session 与 Web UI

如果对应 Channel Session 正确映射为：

```text

```

理论模型：

```text

├── Group 1
│   └── Session 1
│
├── Group 2
```

# 44. Group Server 才是真实聊天记录源

需要继续明确：

## Platform

保存：

> 群里实际上发生了什么。

## OpenClaw

保存：

> 该 Agent 在这个 Group 中所看到和形成的 Session Context。

因此：

```text
Server Message History
```

是 authoritative chat history。

而 OpenClaw Session 是：

```text
Agent-specific conversational state
```

# 54. 多群 Replay

例如 Agent A 属于：

```text
Group 1
Group 2
```

掉线前：

```text
Group 1 lastAck = 100
Group 2 lastAck = 50
```

掉线后：

```text
Group 1 到 105
Group 2 到 57
```

重连后：

```text
Replay Group 1:
101 → 105

Replay Group 2:
51 → 57
```

每个 Group 独立恢复。

# 120. 最终核心架构

最终系统可以概括为：

```text
                          Agent Pool

                   A      B      C      D
                   │      │      │      │
             ┌─────┴──────┴──────┴──────┴─────┐
             │                                 │
             │       Group Chat Platform       │
             │                                 │
             └───┬──────────┬──────────┬───────┘
                 │          │          │
                 ↓          ↓          ↓

             Group 1     Group 2     Group 3

             Human A     Human B     Human C
             Agent A     Agent A     Agent B
             Agent B     Agent C     Agent C
             Agent D     Agent D     Agent A
```

以上成员组合仅为示意。

真正的系统模型是：

```text
Human ↔ Group = Many-to-Many

Agent ↔ Group = Many-to-Many
```

而 OpenClaw 一侧：

```text
Agent A

Group 1 → Session 1

Group 2 → Session 2

Group 3 → Session 3
```

最终实现的不是一个固定“大群机器人 Demo”，而是：

> **一个可以把已经接入的 OpenClaw Agent 当作可复用智能成员，由不同 Human 自由组建不同群聊协作空间的演示平台。**

每个群拥有自己的成员、消息历史和 Agent Session 上下文。

同一个 Agent 可以同时服务多个群。

多个 Human 可以分别建立自己的 Agent 工作群。

需要时，也可以创建包含多个 Human 与多个 Agent 的共同群聊。

所有 Agent 的名称、角色、数量、职责和具体群成员组合，均由实际 Demo 管理员自行配置；本文中的任何成员名称和组合均仅用于说明系统行为。
